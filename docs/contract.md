# Контракт гарячого шляху

Домовленість між редірект-сервісом (зараз ізольований шматок Laravel, згодом Go) і рештою Laravel.
Сторони спілкуються **тільки** через Redis і спільну БД. Усе, що не описано тут, — внутрішня справа кожної сторони.

Версія контракту: **1**. Постбеки описуються в етапі 3.

---

## Терміни

- **Джерело трафіку** — рекламна мережа, де ми купуємо покази (наприклад, пуш-мережа).
- **Макрос** — плейсхолдер джерела в лінку, наприклад `{zoneid}`. У момент кліку джерело підставляє в нього реальне значення.
- **Зона** — майданчик (сайт/застосунок), де показали рекламу. **Креатив** — конкретне оголошення. Обидва приходять через макроси й потрібні, щоб знайти збиткові зони та креативи.
- **CPA-мережа** — партнерська мережа, яка платить за дію (реєстрація, депозит тощо). Дає **оффер** — посилання на цільову сторінку.
- **click_id** — унікальний ідентифікатор нашого кліку. Ми передаємо його в URL оффера, CPA-мережа повертає його в постбеку, і так конверсія прив'язується до кліку.
- **Постбек** — серверний запит від CPA-мережі до нас: «по click_id X сталася конверсія зі статусом Y».
- **Fallback URL** — куди відправити відвідувача, якщо кампанія невідома чи вимкнена.

---

## Потік кліку

```
джерело → GET /c/{alias}?zone=...&creative=...
            │
            ├─ HGET spread:config:campaigns {alias}   (знімок конфігу)
            ├─ XADD spread:clicks * payload {JSON}      (буфер кліків)
            └─ 302 → URL оффера з click_id
                         
Laravel-воркер ← XREADGROUP spread:clicks → INSERT у БД (+ гео, пристрій, боти) → XACK + XDEL
```

---

## Redis-ключі

Ключі абсолютні: без префікса фреймворку (Laravel-префікс `REDIS_PREFIX` для цих операцій не застосовується).

| Ключ | Тип | Пише | Читає |
|---|---|---|---|
| `spread:config:campaigns` | Hash: `alias` → JSON кампанії | Laravel | редірект |
| `spread:config:meta` | String: JSON | Laravel | редірект |
| `spread:clicks` | Stream, поле `payload` = JSON кліку | редірект | Laravel-воркер |
| `spread:clicks:dead` | Stream, поля `payload`, `reason` | Laravel-воркер | людина / адмінка |

## Знімок конфігу

### `spread:config:campaigns`

Hash, де поле — alias кампанії, значення — JSON:

```json
{
  "id": 12,
  "offer_id": 5,
  "active": true,
  "offer_url": "https://offer.example/lp?sub1={click_id}&sub2={zone}"
}
```

- `id`, `offer_id` — ідентифікатори в БД; редірект кладе їх у клік, щоб клік пам'ятав, на який оффер він пішов, навіть якщо кампанію потім переналаштують.
- `active: false` — кампанія вимкнена (див. поведінку нижче). Видалені кампанії в знімок не потрапляють.
- `offer_url` — шаблон URL оффера з плейсхолдерами (правила підстановки нижче).

### `spread:config:meta`

```json
{
  "v": 1,
  "version": 1758700000123,
  "generated_at": "2026-09-24T10:15:30.123Z",
  "fallback_url": "https://example.com/"
}
```

- `version` — мітка часу побудови знімка в мілісекундах; змінюється при кожній перебудові. Go перечитує `meta` раз на кілька секунд і забирає `HGETALL spread:config:campaigns` лише коли `version` змінився.

### Як Laravel оновлює знімок

- При створенні, зміні чи видаленні кампанії або оффера, а також командою `php artisan spread:config:rebuild`.
- Атомарно: повний hash будується в `spread:config:campaigns:tmp`, далі одна транзакція `MULTI` → `RENAME tmp → spread:config:campaigns` → `SET spread:config:meta` → `EXEC`. Читач ніколи не бачить напівзаписаний знімок.
- Побудова tmp теж іде всередині цієї транзакції: `MULTI` → `DEL tmp` → `HSET tmp <усі поля>` → `RENAME` → `SET meta` → `EXEC`. Так дві одночасні перебудови не змішують поля в tmp.
- Кампаній немає → замість `HSET` і `RENAME` у транзакції `DEL spread:config:campaigns`, записується лише `meta`. Для редіректу відсутній hash означає «alias немає в знімку».

## Редірект

`GET /c/{alias}` — усі query-параметри вважаються параметрами джерела.

| Ситуація | Клік у буфер | Відповідь |
|---|---|---|
| кампанія є, `active: true` | так, `status: "ok"` | 302 на URL оффера |
| кампанія є, `active: false` | так, `status: "campaign_disabled"` | 302 на `fallback_url` |
| alias немає в знімку | ні | 302 на `fallback_url` |
| Redis недоступний / немає `meta` | ні (клік втрачено) | 302 на fallback URL з власного конфігу редіректу |

- Відповідь завжди `302` з `Cache-Control: no-store`.
- `HEAD /c/{alias}` відповідає тим самим `302` і тим самим `Location`, що й `GET`, але клік у буфер **не пише**: HEAD шлють перевірки посилань і модерація рекламних мереж, а не відвідувачі.
- Клік пишеться в буфер **до** відповіді. Жодних звернень до БД.
- Останній рядок таблиці — свідомо прийнята втрата для Laravel-версії. Go-версія (етап 8) замість цього писатиме клік у локальний файл.

### Підстановка в `offer_url`

- Плейсхолдер — це `{` + ім'я з `[A-Za-z0-9_]`, від 1 до 64 символів, + `}`. Будь-який інший текст у фігурних дужках лишається як є.
- `{click_id}` → click_id цього кліку, навіть якщо в запиті є параметр `click_id`.
- `{name}` → значення параметра `name` з запиту (після лімітів), URL-закодоване за RFC 3986: пробіл → `%20`, не `+`. Параметра немає → порожній рядок.
- Регістр імен важливий, інших конструкцій немає.

### Розбір query-параметрів

- Параметри розбираються із сирого рядка запиту: пари розділено `&`, ім'я від значення — першим `=`, пара без `=` дає порожнє значення.
- Ім'я і значення декодуються як `application/x-www-form-urlencoded`: `+` — пробіл, `%XX` — байт.
- Ім'я зберігається як є, без перетворень (`a.b`, `sub[1]` — звичайні рядки, не масиви). Пара з порожнім ім'ям ігнорується.
- Для повторюваного імені береться останнє значення.

### Ліміти

Редірект обрізає, а не відкидає. Символ — це символ Unicode (не байт); некоректні UTF-8 послідовності спершу замінюються на U+FFFD, потім рахуються ліміти.

| Що | Ліміт |
|---|---|
| кількість параметрів | 50 різних імен у порядку першої появи (решта ігнорується) |
| ім'я параметра | 64 символи |
| значення параметра | 1024 символи |
| `user_agent` | 1024 символи |
| `referer` | 2048 символів |

Значення передаються як є: порожні рядки й непідставлені макроси (`{zoneid}`) не інтерпретуються, це робота воркера.

## Повідомлення про клік

`XADD spread:clicks * payload <JSON>`. Продюсер стрім **не обрізає** (`MAXLEN` не використовується).

```json
{
  "v": 1,
  "click_id": "01J8Z3K4M5N6P7Q8R9S0T1V2W3",
  "ts": "2026-09-24T10:15:30.123Z",
  "status": "ok",
  "campaign_id": 12,
  "offer_id": 5,
  "ip": "203.0.113.5",
  "user_agent": "Mozilla/5.0 ...",
  "referer": null,
  "params": { "zone": "8841", "creative": "17" }
}
```

| Поле | Тип | Зміст |
|---|---|---|
| `v` | int | версія формату повідомлення |
| `click_id` | string | ULID, 26 символів Crockford base32, генерує редірект; час у ULID = `ts` |
| `ts` | string | час кліку, UTC, ISO 8601 з мілісекундами |
| `status` | string | `ok` \| `campaign_disabled` |
| `campaign_id`, `offer_id` | int | зі знімка на момент кліку |
| `ip` | string | IP відвідувача; за nginx береться з `X-Real-IP` (nginx сам виставляє його з адреси з'єднання, затираючи заголовок клієнта); заголовка немає → `""` |
| `user_agent`, `referer` | string \| null | заголовки запиту, `null` якщо відсутні |
| `params` | object string→string | усі query-параметри; для повторюваних ключів — останнє значення |

Гео, пристрій, ОС, браузер, позначки ботів і дублів у повідомленні **немає** — їх обчислює воркер.

## Воркер кліків

- Consumer group `db` на `spread:clicks`, створюється воркером на старті: `XGROUP CREATE spread:clicks db 0 MKSTREAM` (помилка `BUSYGROUP` = група вже є).
- Гарантія **at-least-once**: запис у БД іде з `ON CONFLICT (click_id) DO NOTHING`, тому повторна обробка не створює дублів.
- Після успішного запису пачки: `XACK`, потім `XDEL` тих самих id — стрім не росте.
- Повідомлення, що зависли в pending після падіння воркера, забираються через `XAUTOCLAIM` (простій понад 60 с).
- Невалідний JSON або невідома `v` → запис у `spread:clicks:dead` з `reason`, потім `XACK` + `XDEL`. Нічого не губиться мовчки.
- Так само в `spread:clicks:dead` іде запис без поля `payload` (`payload` у dead — порожній рядок) і повідомлення відомої `v`, у якому бракує обов'язкового поля або поле має не той тип, що в таблиці повідомлення.
- `XLEN spread:clicks` — розмір черги, що чекає на обробку; основа для алерту «переповнений буфер» (етап 6).

---

## Версіонування

- Нове **необов'язкове** поле — `v` не змінюється; споживач ігнорує незнайомі поля.
- Перейменування, видалення поля чи зміна його змісту — `v` + 1. Воркер має вміти читати і стару, і нову версію, доки в стрімі можуть лишатися старі повідомлення.
- Зміни контракту вносяться в цей файл у тому ж коміті, що й код.
